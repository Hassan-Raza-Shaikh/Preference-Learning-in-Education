## 1. The idea in one paragraph

We want an AI tutor that **teaches each child the way that child learns best**. It should
explain concepts (not just give answers). It should notice how a learner prefers to be
taught, for example which method, how much step-by-step detail and what pace, and adapt to
it. Its mathematics must never be wrong. Over time it should **build the child's ability**,
not only answer the current question. Later, the same approach should extend to other
subjects and run at school level, with teachers able to configure it for their class.

We pursue this as both:
- **A practical system:** a working tutor that a school can use, starting with a
  proof of concept.
- **A research programme:** each stage should produce findings we can publish (workshop
  paper, conference paper, journal article).

**Opportunity:** our supervisor reports that **a school is willing to provide data and
support if the proof of concept works.** So the next milestone is a convincing proof of
concept (Section 5).

## 2. What "preference learning" means here (and how Phase 1 drifted)

The term has two meanings, and Phase 1 tested the one we did not mean.

| | **Learner preference** (our goal) | **Preference optimisation** (what Phase 1 tested) |
|---|---|---|
| Whose preference? | The child's: which explanation helps *them* | A label saying "the correct solution beats the broken one" |
| Signal | What the child chooses, rates, and then gets right | Correct vs. deliberately corrupted solution |
| Purpose | Personalise *teaching* | Make the model more *accurate* |
| Measured by | Does the child understand / improve? | Does the model get the final answer right? |

Phase 1 (see [`02_PHASE1_METHOD_CONDITIONED_SOLVING.md`](02_PHASE1_METHOD_CONDITIONED_SOLVING.md))
used DPO with correct-vs-incorrect pairs. That is really a *correctness* signal, and sympy
already checks correctness perfectly. The finding that DPO hurt small models is a valid
research result. It does not, however, address personalisation.

**Reframing.** Correctness is a hard **floor**, guaranteed by the verified sympy engine
from Phase 1. Preference then chooses **which correct explanation** a given learner sees.
The two concerns are handled separately:

```
            ┌──────────────────────────────────────────────┐
problem ──▶ │ Verified engine (Phase 1): every method /    │──▶ several explanations,
            │ format generated by sympy and checked        │    ALL guaranteed correct
            └──────────────────────────────────────────────┘
                                   │
                                   ▼
            ┌──────────────────────────────────────────────┐
learner ──▶ │ Learner model:                               │──▶ the explanation THIS
history     │  • mastery per skill (knowledge tracing)     │    learner gets, plus the
            │  • preference per explanation style          │    next problem to practise
            └──────────────────────────────────────────────┘
                                   │
                                   ▼
               learner chooses / rates / answers a check question
                                   │
                                   └──────▶ updates the learner model (loop)
```

The ML-style preference learning from Phase 1 returns later, in its proper role. Once we
have **real learner preference pairs** ("learner chose explanation A over B, and then
answered correctly"), the existing DPO pipeline can train a model on *pedagogical*
preferences instead of correctness.

## 3. A caution we must design around: "learning styles"

Matching teaching to a learner's self-reported "learning style" (visual, auditory and so on)
has been tested extensively and **generally does not improve learning** (Pashler, McDaniel,
Rohrer & Bjork, 2008, *Psychological Science in the Public Interest*). Education reviewers
will raise this. So we personalise on dimensions that have evidence behind them, and we
**measure learning, not just satisfaction**:

| Dimension | Example | Why it is defensible |
|---|---|---|
| Solution method | substitution vs. elimination vs. matrices | Different methods suit different problems and learners; we already generate all of them, verified |
| Amount of scaffolding | full worked example → partial hints → just a check | "Expertise reversal effect": worked examples help novices, but fade-out helps once skill grows |
| Pacing / next problem | harder vs. easier, more practice on a weak skill | Knowledge tracing (OATutor already ships BKT parameters) |
| Context / interest | word problems themed on the learner's interests | Context personalisation has supporting studies; keep the maths identical |

"Build the child's aptitude" maps onto **knowledge tracing**: estimate mastery per skill,
practise weak skills and fade support as mastery rises.

## 4. Two tracks

### Track A: continue the Phase 1 research (method-conditioned solving)
We keep this going because it is the correctness backbone and a publishable result in itself.
Open items are listed in the Phase 1 document, Section 8. The highest-value items:
1. Diagnose *why* DPO hurt (the preference pairs share most tokens with the correct
   solution and are not the model's own outputs; see the Phase 1 document).
2. A real method-faithfulness metric, beyond keyword matching.
3. Several seeds per condition.
4. Parse more of the 751 OATutor systems (only 164 are used today).

### Track B: proof of concept for the school (new)
The personalised, verified tutor loop from Section 2, for one topic first.

## 5. Proof-of-concept plan (Track B)

**Scope:** one topic, *systems of linear equations* (algebra, roughly grades 8–10), where
all our verified data already lives. Expand to other subjects only after the loop works.

**What the proof of concept must demonstrate to a school:**
1. **Never wrong.** Every explanation is generated and verified by sympy. Zero incorrect
   maths shown.
2. **Adapts.** Different learners end up with different explanation styles and problem
   sequences, driven by their choices and results.
3. **Builds skill.** Mastery estimates rise, and support fades as they do.
4. **Teacher control.** A teacher can configure which methods, how much scaffolding and
   which skills, without code ("custom way").
5. **Measurable.** Everything is logged, so a school study can measure learning gains.

**On M4 (honesty note):** simulated learners show that the *machinery works*: preferences
are detected and adaptation happens. They do **not** show that real children learn more.
That claim requires the school study. We will say this explicitly in every report.

### Model choice for the prototype
Phase 1 showed that small (1.5B) models fine-tuned on a laptop lose accuracy. For the proof
of concept, the maths comes from the **verified engine**. Natural-language explanation text
is either (a) templated from the engine, or (b) written by a strong existing LLM that is
given the verified steps and only allowed to explain them. Every number it states is
re-checked. Fine-tuning comes later, once real learner preference data exists.

## 7. Ethics and data (start early)

Working with children's data requires: institutional ethics approval, parental consent and
child assent, data minimisation (pseudonymous IDs, no unnecessary personal data), secure
storage, and an agreement with the school. Documents for this are part of M5. They should
be drafted **before** the school is asked for data.
